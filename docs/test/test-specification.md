## 1. 方針

要件定義書 13.1 のとおり、要件 ID ごとに 1 件以上のテストを用意する。テストはできるだけ自動にし、Pull Request ごとに GitHub Actions で動かす（N-24）。

| 種類 | 何を確かめるか | 置き場所 | いつ動かすか |
| --- | --- | --- | --- |
| API | API の入力・出力・権限・データ（Controller・Service・Repository の単体と、API を通したもの）。DB は Testcontainers の PostgreSQL、S3 は MinIO | backend/src/test/java | Pull Request ごと（`mvnw verify`） |
| 画面 | 画面の部品と画面ごとの動き。API は偽物にする | frontend/src/\*\*/\*.test.ts(x) | Pull Request ごと（`npm test`） |
| E2E | 本物の API・DB につなぎ、ブラウザで利用者の操作の流れを確かめる。アクセシビリティ（axe）と 375px の横幅も | frontend/e2e | Pull Request ごと（CI は Edge。ほかのブラウザは 3 章） |
| 性能 | 要件定義書 11.1（N-1〜N-5）の時間を P95 で判定する | perf/k6、frontend/perf | 任意のとき（基本設計書 2.4、[性能テスト報告書](performance-test-report.md)） |
| テスト以外 | 設定・文書を見る、公開先で確かめる | | 検収のとき（開発計画書 3-3d） |

## 2. 要件 ID とテストの対応

### 2.1 テストに要件 ID・観点の ID を書く決まり

テストを書くときは、確かめる要件 ID（A・T・W・I・C・L・F・S・PF・G・M・N・BR。docs/README.md の ID の一覧）と、機能定義書 10 章のテストの観点の ID（TC-機能の番号-連番。例：TC-03-1）を、次のどこかに書く。

| 書く場所 | 例 | どのテストに付くか |
| --- | --- | --- |
| テストの名前 | `it('M-6：ユーザー ID かパスワードが違うときは…')`、`test('N-10 ログインしていないと…')` | そのテスト |
| テストの直前のコメント | `// BR-6`（JUnit では `@Test` の上でもよい） | 次のテスト |
| テストの中 | `// M-11` | そのテスト |
| 区切りのコメント | `// ---- 登録（A-1〜A-4）----` | 次の区切りまでのテスト |
| describe・@Nested のクラス名 | `describe('ログインの画面（A-5〜A-7）', …)` | 次の区切りまでのテスト |

`A-1〜A-4`・`TC-03-1〜3` のように範囲でも書ける。

### 2.2 対応表

[要件 ID とテストの対応表](requirement-coverage.md) は、`node scripts/requirement-coverage.mjs` がテストのファイルを読んで作る。手で直さない。

- 対応表は 1 章が要件 ID、2 章がテストの観点（機能定義書 10 章）。どちらも、確かめるテストを種類（API・画面・E2E・性能）ごとに並べる
- テストのない要件 ID・観点があるとき、または対応表を作り直していないときは、`node scripts/requirement-coverage.mjs --check` が失敗する。GitHub Actions でも Pull Request ごとに動かす
- テストではなく、設定・文書を見て確かめる要件 ID（N-6・N-7・N-9・N-16・N-17・N-21〜N-24）は、確かめ方を対応表に書く（スクリプトの中の一覧で決める）
- テストの観点のうち、目で見て確かめるもの（TC-04-11 画像の並べ方）は 4 章の手動の項目にする（スクリプトの中の一覧で決める）
- 要件 ID の種類のうち、P（前提）・R（リスク）・U（未決事項）・Q（設計で見つけた不足）・SG（セキュリティグループ）は、テストの対象にしない。SG はインフラ設計書と Terraform の検査（tflint・trivy）で確かめる

## 3. 環境ごとの結果

### 3.1 対応環境と、代わりに確かめた環境

要件定義書 3.2 の 7 つの環境のうち、作成者のパソコン（Windows 11）にあるのは Windows のブラウザだけである。利用者の決定（2026-10-31）で、ほかの環境は次の代わりのブラウザで E2E を流し、実機は 4 章の手順で利用者が確かめる。

| No | 対応環境 | 代わりに確かめた環境（Playwright の project） | 画面の幅 | 流すテスト |
| --- | --- | --- | --- | --- |
| 1 | Windows 11・Google Chrome | Chrome 156（chrome） | 1280px | E2E すべて |
| 2 | Windows 11・Microsoft Edge | Edge 156（pc・mobile。CI も） | 1280px・375px | E2E すべて（375px は主な流れと全画面） |
| 3 | Windows 11・Mozilla Firefox | Playwright の Firefox 155（firefox） | 1280px | E2E すべて |
| 4 | macOS・Safari | Playwright の WebKit 26.6（webkit。Safari と同じエンジン） | 1280px | E2E すべて |
| 5 | macOS・Google Chrome | No.1 と同じ（Chrome は OS で動きが変わらない） | | |
| 6 | iOS・Safari | WebKit 26.6 で iPhone 15 の大きさ・User-Agent・タッチ（iphone） | 393px | 主な流れと全画面 |
| 7 | Android・Google Chrome | Chrome 156 で Pixel 7 の大きさ・User-Agent・タッチ（android） | 412px | 主な流れと全画面 |

流し方：3 つのサーバー（DB・API・画面）を起動し、frontend で `E2E_BROWSERS=all npx playwright test`（PowerShell では `$env:E2E_BROWSERS='all'; npx playwright test`）。Firefox と WebKit は先に `npx playwright install firefox webkit` で入れる。この流し方のときだけ、落ちたテストを 1 回やり直す（パソコンが忙しいと WebKit がたまに止まるため）。やり直して通ったものは「flaky」と出るので、結果に書く。

### 3.3 流す中で見つけて直したこと

どれもテストの書き方の問題で、アプリの不具合ではなかった。

| 見つけたこと | 原因 | 直したこと |
| --- | --- | --- |
| WebKit で、ボタンを押す操作が 30 秒で止まる（テストによって違う） | テストで開いたブラウザを閉じずに残していた。開いたままの画面がたまり、WebKit では描画が止まった | テストが終わるたびに、開いたブラウザを閉じる（e2e/helpers.ts の closeContexts） |
| WebKit で、検索し直した結果の「フォロー中」が「フォロー解除」になる | 前に押したボタンの位置にマウスが残り、同じ位置に来たボタンにマウスが乗った扱いになった（マウスを乗せると「フォロー解除」になる仕様どおり） | 確かめる前にマウスを画面の外へ動かす |
| WebKit で、フォローの直後に API で読んだ数が 1 つ少ない | 画面は応答を待たずに表示を変える（楽観的な表示）ので、DB に入る前に読んでいた | DB に入るまで待って確かめる（expect.poll） |

ほかに、全部を続けて流してパソコンが忙しいとき、iPhone のエミュレーションで、投稿の詳細画面を開いた直後に入れたコメントが入らず「コメントする」が押せないままになることが 2 回あった。そのテストだけを 11 回流し直したときは起きず、原因は分かっていない。実機で確かめる項目（4.1 の No.8）に入れた。

## 4. 手動で確かめる項目

### 4.1 実機（利用者が確かめる）

対応環境のうち、代わりの環境で確かめた macOS（Safari・Chrome）・iOS（Safari）・Android（Chrome）は、検収のとき（開発計画書 3-3d）に公開先の URL を実機で開いて、次を確かめる。ユーザーは 2 人作る（2 台目の端末か、パソコンのブラウザを使う）。

| No | 操作 | 確かめること | 関係する ID |
| --- | --- | --- | --- |
| 1 | ユーザー登録する。ユーザー ID を 2 文字にして「登録する」 | 入力欄の下に M-2 が出る。正しく直すと登録できて G-3 に移る | A-1〜A-4、M-2 |
| 2 | ログアウトして、パスワードを間違えてログインする | フォームの上に M-6 が出る。正しいパスワードでログインできる | A-5〜A-7、M-6 |
| 3 | ブラウザを閉じて開き直す | ログインしたまま G-3 が出る | A-8 |
| 4 | 端末の写真から画像を 4 枚選んで投稿する（スマートフォンはカメラロールから） | プレビューに 4 枚出て、投稿するとタイムラインに 4 枚が出る | I-1〜I-4、N-4 |
| 5 | 1〜4 枚の投稿を見る。画像を押す | 並べ方が画面設計書 3.7 のとおり。G-10 で大きく出て、左右に切り替え・閉じられる | TC-04-11、G-10 |
| 6 | もう 1 人のユーザーで検索してフォローし、「フォロー中」タブを開く | 相手の投稿が出る | S-1〜S-9、F-1〜F-5、T-1 |
| 7 | 「♡」を押す。もう一度押す | すぐに「♥」と数が変わり、もう一度で戻る | L-1、L-2、N-3 |
| 8 | 投稿の詳細画面を開いて、すぐにコメントを書いて「コメントする」 | 書いた文字が残っていて、コメントが一覧に出る（3.3 のエミュレーションでの現象が実機で起きないか） | C-1〜C-3 |
| 9 | 自分の投稿を「…」から削除する | 確認ダイアログに M-10 が出て、「削除」で消える | W-7、M-10、N-19 |
| 10 | プロフィールを編集して、アイコンを端末の写真から選ぶ | ヘッダー・投稿カードのアイコンが変わる | PF-8〜PF-10 |
| 11 | どの画面も、縦に持って（スマートフォン）・画面の拡大率を 150% にして（パソコン）見る | 横にスクロールせず、文字が切れない。文字はすべて日本語 | N-17、N-20、3.2 の拡大率 |
| 12 | 通信を切る（機内モード）。戻す | お知らせ欄に M-20 が出て、戻すと消える | M-20 |
