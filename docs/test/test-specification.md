## 1. 方針

要件定義書 13.1 のとおり、要件 ID ごとに 1 件以上のテストを用意する。テストはできるだけ自動にし、Pull Request ごとに GitHub Actions で動かす（N-24）。

| 種類 | 何を確かめるか | 置き場所 | いつ動かすか |
| --- | --- | --- | --- |
| API | API の入力・出力・権限・データ（Controller・Service・Repository の単体と、API を通したもの）。DB は Testcontainers の PostgreSQL、S3 は MinIO | backend/src/test/java | Pull Request ごと（`mvnw verify`） |
| 画面 | 画面の部品と画面ごとの動き。API は偽物にする | frontend/src/\*\*/\*.test.ts(x) | Pull Request ごと（`npm test`） |
| E2E | 本物の API・DB につなぎ、ブラウザで利用者の操作の流れを確かめる。アクセシビリティ（axe）と 375px の横幅も | frontend/e2e | Pull Request ごと（CI は Edge。ほかのブラウザは 3 章） |
| 性能 | 要件定義書 11.1（N-1〜N-5）の時間を P95 で判定する | perf/k6、frontend/perf | 任意のとき（基本設計書 2.4、[性能テスト報告書](performance-test-report.md)） |
| テスト以外 | 設定・文書を見る、公開先で確かめる | | 検収のとき（開発計画書 3-3d） |

## 2. 要件 ID とテストの対応

### 2.1 テストに要件 ID を書く決まり

テストを書くときは、確かめる要件 ID（A・T・W・I・C・L・F・S・PF・G・M・N・BR。docs/README.md の ID の一覧）を、次のどこかに書く。

| 書く場所 | 例 | どのテストに付くか |
| --- | --- | --- |
| テストの名前 | `it('M-6：ユーザー ID かパスワードが違うときは…')`、`test('N-10 ログインしていないと…')` | そのテスト |
| テストの直前のコメント | `// BR-6`（JUnit では `@Test` の上でもよい） | 次のテスト |
| テストの中 | `// M-11` | そのテスト |
| 区切りのコメント | `// ---- 登録（A-1〜A-4）----` | 次の区切りまでのテスト |
| describe・@Nested のクラス名 | `describe('ログインの画面（A-5〜A-7）', …)` | 次の区切りまでのテスト |

`A-1〜A-4` のように範囲でも書ける。

### 2.2 対応表

[要件 ID とテストの対応表](requirement-coverage.md) は、`node scripts/requirement-coverage.mjs` がテストのファイルを読んで作る。手で直さない。

- テストのない要件 ID があるとき、または対応表を作り直していないときは、`node scripts/requirement-coverage.mjs --check` が失敗する。GitHub Actions でも Pull Request ごとに動かす
- テストではなく、設定・文書を見て確かめる要件 ID（N-6・N-7・N-9・N-16・N-17・N-21〜N-24）は、確かめ方を対応表に書く（スクリプトの中の一覧で決める）
- 要件 ID の種類のうち、P（前提）・R（リスク）・U（未決事項）・Q（設計で見つけた不足）・SG（セキュリティグループ）は、テストの対象にしない。SG はインフラ設計書と Terraform の検査（tflint・trivy）で確かめる
