## 1. 概要

### 1.1 背景

本アプリは学習課題として作成する。作成を通して、複数の利用者が使う Web アプリの開発（Spring Boot・React・PostgreSQL）と、クラウド（AWS）を使った画像の保存・公開の基礎を習得する。

既存の SNS（X など）には、次の点で使いにくさがある。

- 投稿ごとにインプレッション数（表示された回数）が出るため、数字を気にして投稿しにくい
- リツイート（再投稿）で他人の投稿が次々に流れてきて、フォローした人の言葉が埋もれる

### 1.2 目的

1. 短い文章と画像を投稿し、フォローした人の投稿を新しい順に読めるようにする
2. いいね・コメントの件数と中身を誰でも見られるようにし、投稿への反応を第三者にも分かるようにする
3. インプレッション数とリツイートをなくし、数字や拡散を気にせず投稿できるようにする

## 5. 用語

| 用語 | 意味 |
| --- | --- |
| ユーザー | アカウントを登録した人 |
| ユーザー ID | ログインとプロフィールの URL に使う、ほかと重ならない英数字の名前。画面では @ を付けて出す（例：@taro_y） |
| 表示名 | 投稿やコメントに出す名前。ほかの人と同じでもよい（例：たろう） |
| 投稿 | ユーザーがタイムラインに出す文章。画像を 4 枚まで添えられる。本文はあとから直せる（編集）が、画像は変えられない |
| タイムライン | 投稿を新しい順に並べた一覧。「フォロー中」と「すべて」の 2 つのタブがある |
| フォロー | ほかのユーザーの投稿を「フォロー中」タブに出すための登録。相手の承認はいらない |
| フォロー中・フォロワー | 自分がフォローしている人／自分をフォローしている人 |
| コメント | 投稿に付ける文章の返信。コメントへのコメントはできない |
| いいね | 投稿への好意の印。1 人 1 投稿に 1 つ。取り消せる |
| 第三者 | その投稿の投稿者でも、いいね・コメントした本人でもないユーザー |
| ユーザー検索 | 入力した文字を、ユーザー ID か表示名に含むユーザーを探すこと |
| アイコン | プロフィールに設定する、その人を表す丸い画像。設定していない人は表示名の頭文字を丸の中に出す |
| 署名付き URL | 一定時間だけ使える、S3 の画像を表示するための URL。期限が切れると開けなくなる |
| JWT | ログインした人が誰かを表す、改ざんを見破れる署名つきの文字列（JSON Web Token）。本アプリでは、ログインの状態をサーバーに覚えさせずに、この文字列で確かめる |
| 確認ダイアログ | 操作を実行する前に「よろしいですか？」と確認する小さな画面 |
| トリム | 入力した文字の前後にある空白（半角・全角スペース、タブ、改行）を取り除くこと |
| 文字数 | Unicode の文字（コードポイント）の数。漢字・ひらがな・英数字は 1 文字。絵文字の一部（肌の色を変えたもの、国旗など）は、見た目は 1 文字でも 2 文字以上として数える |

## 6. 利用の流れ

1. ブラウザでアプリの URL を開く
2. 初めての場合は「アカウントを作る」からユーザー登録する。2 回目以降はユーザー ID とパスワードでログインする
3. タイムラインが表示される
4. ヘッダーの検索欄で知り合いを探し、プロフィールの「フォローする」でフォローする
5. 文章や画像を投稿する。フォローした人の投稿は「フォロー中」タブに、全員の投稿は「すべて」タブに出る
6. 気になる投稿にいいね・コメントする。ほかの人がいいね・コメントした内容も見られる
7. 共用のパソコンで使った場合は、最後にログアウトする

## 9. データ要件

扱うデータは、ユーザー・投稿・画像・コメント・いいね・フォローと、ログインを続けるためのリフレッシュトークンである。上限は、投稿とコメント 280 文字、画像 1 投稿 4 枚・1 枚 5MB、アイコン画像 1 枚 5MB とする。保存する個人情報は、ユーザー ID・表示名・自己紹介・アイコン画像とパスワード（元に戻せない形）のみとする。

項目・上限・個人情報の詳細は[データ要件定義書](data-requirements.md)に、データの構造（ER 図）は[データ設計書](../design/data-design.md)に書く。

## 11. 非機能要件

### 11.1 性能

次の条件で測定する：ユーザー 1,000 人・投稿 1 万件・コメント 3 万件・いいね 5 万件、測定するユーザーのフォロー 1,000 人、3.2 の対応環境、下り 10Mbps 以上・上り 30Mbps 以上の回線。

| ID | 内容 | 目標値 |
| --- | --- | --- |
| N-1 | ログインしてからタイムラインの最初の 20 件が表示されるまで | 3 秒以内 |
| N-2 | タイムラインの 20 件を返す API の応答（「フォロー中」「すべて」とも） | 1 秒以内 |
| N-3 | いいね・フォローを押してから画面に反映されるまで | 0.5 秒以内 |
| N-4 | 画像 4 枚（合計 20MB）の投稿を押してから、タイムラインに出るまで | 10 秒以内 |
| N-5 | ユーザー検索の結果が表示されるまで | 1 秒以内 |

判定のしかた（版数 0.10）：

| 項目 | 決めたこと |
| --- | --- |
| 判定 | 同じ操作を繰り返し測り、P95（小さい順に並べて 95% の位置の値。20 回なら遅い方から 2 番目）が目標値以内なら合格とする。平均では、一部の遅い操作が隠れるため |
| 回線 | 上りの条件（30Mbps 以上）を足した。N-4 は 20MB を送るので、上り 10Mbps では送るだけで 16 秒かかり、目標を満たせないため |
| 「表示されるまで」（N-1・N-4） | 投稿のカード（文字と画像の枠）が出るまで。画像は S3 から遅れて届き、20MB を下り 10Mbps で読むだけで約 16 秒かかるため、画像の読み込みが終わるまでは参考として記録する |
| N-3 | 画面は押した直後に表示を変える（楽観的な表示）ので、表示が変わるまでと、サーバーの応答で確定するまでの両方を 0.5 秒以内とする |
| 合否を決める環境 | 公開先（AWS）で測った値。手元や GitHub Actions のランナーで測った値は参考とする |
| 測り方 | [基本設計書](../design/basic-design.md) 2.4 |

### 11.2 可用性・データ保全

| ID | 内容 |
| --- | --- |
| N-6 | 稼働時間は AWS の稼働に従う。本アプリ独自の稼働率の目標は設けない。費用を抑えるために止めている間（P-4）は使えない |
| N-7 | データベースは 1 日 1 回自動でバックアップし、7 日分を残す（RDS の自動バックアップ）。ただし AWS が無料プランの間は、無料プランの上限のため 1 日分だけを残す（インフラ設計書 7 章）。失われる可能性があるのは、最後のバックアップ以降の変更のみ |
| N-8 | S3 の画像は、投稿を削除したとき（投稿の画像）と、アイコンを変えた・外したとき（前のアイコン）にだけ消す。それ以外で消えないようにする |

### 11.3 セキュリティ

| ID | 内容 |
| --- | --- |
| N-9 | 公開時の通信はすべて HTTPS（暗号化）で行う |
| N-10 | ログインしていない状態では、データの読み書きを一切できない |
| N-11 | 各利用者は、自分の投稿・コメント・いいね・フォロー・プロフィールだけを変更・削除できる。画面だけでなくサーバー側でも確かめる |
| N-12 | パスワードは元に戻せない形（BCrypt）で保存する。そのままの形では保存もログ出力もしない |
| N-13 | 同じユーザー ID で 5 回続けてログインに失敗したら、15 分間そのユーザー ID でログインできないようにする |
| N-14 | 画像を置く S3 は外部から直接読めないようにし、画面には有効期限 15 分の署名付き URL で渡す |
| N-15 | 投稿・コメント・プロフィールの文字は、HTML として解釈させずにそのまま表示する（他人の画面でスクリプトを動かさせない） |
| N-16 | データベースのパスワード、JWT の署名に使う秘密の値、AWS の認証情報は、ソースコードとリポジトリに置かない |
| N-25 | ログインの状態は JWT で持ち、JavaScript から読めない Cookie（HttpOnly）に入れる。JWT の有効期限は 15 分と短くし、ログインしたままにする（A-8）ためには別のリフレッシュトークンを使う。ログアウトしたら、リフレッシュトークンをサーバー側で無効にする |

N-25 は後から足したため、番号は 11.5 の N-24 の続きにした。

## 12. リスクと対策

| No | リスク | 影響 | 対策 |
| --- | --- | --- | --- |
| R-1 | AWS の費用が想定を超える | 費用が発生し続ける | 使わない間は止める（P-4）。AWS Budgets で月 10,000 円を超えそうなときにメールを受け取る。常に動かした場合の見積もりは 約 11,000 円で予算を超えるため、使う時間だけ動かす（インフラ設計書 7 章） |
| R-2 | 誰でも登録できるため、不適切な投稿・画像が載る | ほかの利用者が不快になる、著作権を侵害する | 公開する URL を知り合いにだけ伝える。見つけた場合は作成者がデータベースと S3 から削除する |
| R-3 | パスワードの総当たりで、ほかの人のアカウントに入られる | なりすまして投稿される | ログイン失敗の回数制限（N-13）とパスワードの条件（A-3） |
| R-4 | S3 の画像が外部から見られる | 投稿した画像が漏れる | バケットを非公開にし、署名付き URL で渡す（N-14） |
| R-5 | データベースの障害・操作の誤りでデータが消える | 投稿などが失われる | RDS の自動バックアップから戻す（N-7） |
| R-6 | ブラウザの仕様変更で動きが変わる | 一部の機能が動かなくなる | 保守期間中は不具合として対応する（15 章） |
| R-7 | JWT の署名に使う秘密の値が漏れる、または JWT・リフレッシュトークンが盗まれる | ほかの人になりすまされる | 秘密の値は Parameter Store に置く（N-16）。漏れたときは秘密の値を変えて全員をログアウトさせる。JWT は Cookie（HttpOnly）に入れて JavaScript から読めなくし、有効期限を 15 分にする（N-25）。リフレッシュトークンは使うたびに新しくし、古いものが使われたらその人のトークンをすべて無効にする（データ設計書 BR-9） |

## 13. 受け入れ（検収）

### 13.1 進め方

| 手順 | 内容 | 担当 |
| --- | --- | --- |
| 1 | 本書と詳細文書（1.3）、機能定義書の要件 ID ごとに 1 件以上のテストを用意し、テスト仕様書にまとめる。機能定義書の 10 章（テストの観点）は必ず含める | 作成者 |
| 2 | 3.2 の全 7 環境（OS とブラウザの組み合わせ）でテストし、結果をテスト仕様書に記録する | 作成者 |
| 3 | 納品物（14 章）を渡す | 作成者 |

| 5 | 結果を「合格」または「不合格（不具合の一覧つき）」で作成者に伝える | 検収者 |
| 6 | 合格の場合は、検収書に署名する。これで検収完了とする | 承認者 |

### 13.2 期間

検収期間は、納品した日の翌日から 7 日間とする。延長する場合は、作成者と承認者の両者で合意する。

### 13.3 不具合の重さと扱い

| ランク | 内容 | 例 | 扱い |
| --- | --- | --- | --- |
| A | データが失われる・漏れる、または主な機能が使えない | 投稿が消える、他人の投稿を削除できる、ログインできない | 修正して再テストするまで合格としない |
| B | 機能は使えるが、本書の内容と動きが違う | メッセージが表示されない、281 文字で投稿できる | 修正して再テストするまで合格としない |
| C | 使うのに支障がない見た目の問題 | 文字が 1px ずれる | 修正するかどうか、いつ修正するかを両者で決める |

### 13.4 合格の条件

1. テスト仕様書のすべての項目が全 7 環境で合格している
2. ランク A・B の不具合が残っていない
3. 14 章の納品物がすべてそろっている

### 15.2 保守で行うこと

| 内容 | 期限 |

## 16. 変更管理

承認後に要件を変える場合は、次の手順で行う。

| 手順 | 内容 | 担当 |
| --- | --- | --- |
| 1 | 変更したい内容と理由を、GitHub の Issue に「変更依頼」として書く | 依頼する人（どちらでもよい） |
| 2 | 変更による影響（作業時間、納期、ほかの機能への影響、AWS の費用）を調べ、Issue に書く | 作成者 |
| 3 | 変更するかどうかを決める | 承認者 |
| 4 | 変更する場合は本書・詳細文書（1.3）・機能定義書を書き直し、版数を上げて改訂履歴に記録し、再度承認を受ける | 作成者・承認者 |

版数の上げ方：文言の修正のみは 0.1 上げる（例：1.0 → 1.1）。機能の追加・削除は 1.0 上げる（例：1.1 → 2.0）。

詳細文書を変えた場合は、その文書の版数を上げて改訂履歴に記録する。あわせて本書の版数も上げ、改訂履歴に「どの詳細文書を何版にしたか」を記録する。承認は本書で行うため、本書の版数が要件定義書全体の版数となる。
