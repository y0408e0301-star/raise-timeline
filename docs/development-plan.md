## 1. 本書の目的

どの順番で作るか（段階）と、1 つの Pull Request で何を作るかを決め、いまどこまでできたかが分かるようにする。何を作るかは[要件定義書](requirements/requirements.md)と[機能定義書](functions/function-definition.md)、どう作るかは[基本設計書](design/basic-design.md)と[技術スタック定義書](tech-stack.md)で決めている。

## 2. 進め方の方針

**機能ごとに、API（バックエンド）とそれを使う画面（フロントエンド）を 1 つの Pull Request で作る。**

| 段階 | 作るもの | 理由 |
| --- | --- | --- |
| 段階 1・2 | 機能ごとの API と画面（FN-01〜FN-09 の第 1 版、G-1〜G-11。G-7 を除く） | 1 つの機能を API のテストで固めたら、すぐに本物の API につないだ画面で確かめられる。画面で見つけた問題（例：ブラウザが multipart で改行を CRLF に変える）を、同じ Pull Request の中で API に直せる |
| 段階 3 | 通しのテストと公開 | 登録 → 投稿 → いいね → フォロー → 検索の流れを画面から確かめ（N-24）、AWS に公開する（P-3） |
| 段階 4 | 第 2 版 | プロフィールの編集（PF-5〜PF-10）。この段階の中は、API → 画面の順に作る |

- 版数 0.2 までは「API を全部作ってから画面を作る」順番にしていた。1-1（API）と 2-1（画面の土台と G-1・G-2）はその順番で作った
- 機能どうしの関係で、ある機能の画面の一部が後の機能の API を使うときは、その API を作る行で画面も仕上げる（例：G-3 のタイムラインの一覧は 1-4）。それまでの画面は、その機能で確かめられる範囲だけを出す
- 動きは、API のテスト（MockMvc・Testcontainers）・画面のテスト（Vitest・Testing Library）と、本物の API につないだ画面（Chrome DevTools。スマートフォンの幅も）で確かめる

## 3. 作る順番

1 行を 1 つの Issue・1 つの Pull Request にする。終わったら、その Pull Request の中で「状態」を ✅ にする。

状態：✅ 終わった、▶ 作業中、空欄 まだ

## 5. 進め方の決まり

- 開発のルール（Issue → ブランチ → Pull Request → squash マージ）は [CONTRIBUTING.md](../CONTRIBUTING.md) のとおり
- 作っている途中で仕様を変えるときは、同じ Pull Request で文書も直す（[CLAUDE.md](../CLAUDE.md)）
- 順番を変えるときや、行を分ける・まとめるときは、本書の版数を上げて改訂履歴に書く
